# ABP Smart Playlists

[![CI](https://github.com/projector22/abp/actions/workflows/ci.yml/badge.svg)](https://github.com/projector22/abp/actions/workflows/ci.yml)
[![License: GPL v3](https://img.shields.io/badge/license-GPLv3-blue.svg)](LICENSE)

Ever wanted a playlist of podcasts, ordered from oldest to newest, to be listened to in that order? That's what I wanted, so I created this tool.

> **Note**: The original version of this tool was built with PHP and was functional, but pretty terrible to use. Therefore this version was build to be much more usable. It was completely generated by Claude. It is useful to me, I put it here on the offchance it's useful to you.
>
> Now read on...

Smart playlists for [Audiobookshelf](https://www.audiobookshelf.org) podcasts, with a TUI.

Pick some podcasts, set a number of episodes, and `abp` keeps a playlist filled with the **oldest unfinished episodes** across them, in publish order. When you finish an episode it drops out on the next sync and the next oldest flows in.

## Install

Download a binary for your platform from the [releases page](https://github.com/projector22/abp/releases), unpack it and put `abp` somewhere on your `PATH`.

Or install with Go:

    go install github.com/projector22/abp@latest

Or build from source (see `make help` for everything else):

    make build       # builds ./abp
    make install     # installs to ~/.local/bin (PREFIX=/usr/local to change)

## Getting started

1. Run `abp`. On first launch it asks for your Audiobookshelf URL and an API key (in Audiobookshelf: Settings → API Keys).
2. Press `n` to create a playlist: give it a name, pick the podcast library, choose how many episodes it should hold and, if you like, a schedule.
3. Tick the podcasts you want in it. Each press of `tab` or `enter` adds or removes one, and it's saved straight away.
4. Press `p` to preview what the playlist will contain, then `s` to sync it to Audiobookshelf.

The playlist list also has a **TO GO** column: the total number of unfinished episodes across a playlist's podcasts (not just the ones that fit within its size), so you can see how far you are from the end. It refreshes in the background after a sync and about once a minute.

From then on abp keeps the same playlist up to date for you. Add a schedule (press `c` on a playlist) and it will do this in the background; otherwise sync by hand with `s`.

## Keys

- **Playlist list:** `enter` open · `n` new · `d` delete · `s` sync · `S` sync all · `C` re-install crontab · `o` server settings · `q` quit
- **A playlist:** `a` add or remove podcasts · `x` remove the highlighted podcast · `e` edit · `c` schedule · `p` preview · `s` sync · `D` delete · `esc` back
- **Podcast picker:** type to filter · `tab`/`enter` toggle a podcast · `esc` done
- **Playlist list:** `enter` open · `n` new · `d` delete · `s` sync · `S` sync all · `C` re-install crontab · `o` server settings · `v` check for updates · `q` quit

## Running on a schedule

Scheduling uses your normal crontab. Set a schedule on a playlist in the TUI and abp adds the crontab entry for you; remove the schedule and the entry goes away. abp only touches its own lines (those ending in `# abp:<id>`), and the rest of your crontab is left alone.

You can also drive it from the command line:

    abp sync history-backlog       # sync one (or several) playlists
    abp sync -all                  # sync everything
    abp sync -n -all               # dry run: show what would change
    abp list                       # list your playlists and their ids
    abp cron install               # make the crontab match your schedules
    abp cron remove                # remove all of abp's crontab entries
    abp cron show                  # show what's installed

Output from scheduled runs is appended to `~/.local/share/abp/abp.log`.

## Version and updates

    abp -v

shows which version you're running and whether there is a newer release:

- **A tagged release** (e.g. `v0.1.4`): tells you if you're up to date, or if an update is available and how to get it.
- **A development build** (built from source with extra commits, or installed from an untagged commit): reported as a development build, and as ahead of the latest release if it is.

The same information is in the TUI: the version is shown at the top right, with an `↑ v0.1.5 available` notice when there is an update, and pressing `v` on the playlist list checks again straight away.

To update, run `go install github.com/projector22/abp@latest` again, or download the new release from the [releases page](https://github.com/projector22/abp/releases).

abp looks for new releases by asking github.com for the latest release page. It asks at most once a day from the TUI, remembers the answer, and sends nothing but a request for that public page. To turn it off completely, set `ABP_NO_UPDATE_CHECK=1`.

## Configuration

Your playlists live in a plain, human-readable file, `~/.config/abp/config.yaml`. You can edit it by hand while abp isn't running:

    playlists:
      - id: history-backlog        # short id used by `abp sync` and the crontab
        name: History Backlog
        description: Slow-burn history, oldest first   # optional, shown in Audiobookshelf
        library: li_abc123
        library_name: Podcasts
        limit: 25                  # most episodes the playlist will hold
        schedule: "*/30 * * * *"   # cron expression; empty = manual only
        podcasts:
          - id: li_def456
            title: Revolutions

Your server URL and API key are kept separately, readable only by you, in `~/.local/share/abp/credentials.json` (deliberately not in `~/.config`, so you can share or back up your config without leaking the key).

| What | Where |
| ---- | ----- |
| Playlists and podcasts | `~/.config/abp/config.yaml` |
| Server URL and API key | `~/.local/share/abp/credentials.json` |
| Sync history | `~/.local/share/abp/state.json` |
| Scheduled-run output | `~/.local/share/abp/abp.log` |

To use different locations, set `ABP_CONFIG` or `ABP_DATA_DIR`. `ABP_URL` and `ABP_API_KEY` override the stored credentials, which is handy with a secrets manager.

## Good to know

- abp owns each playlist's name and description. They are pushed to Audiobookshelf on every sync, so edits made to them in Audiobookshelf itself will be overwritten.
- Audiobookshelf ignores an empty description, so clearing one in abp won't clear it on the server.
- Audiobookshelf deletes a playlist when its last item goes. If you finish every episode the playlist disappears, and abp recreates it when new episodes arrive.
- A playlist belongs to one podcast library, which can't be changed after the playlist is created.
- If a podcast can't be loaded (for example the server is unreachable), the sync stops and leaves your playlist as it was rather than shrinking it. A podcast you've deleted from Audiobookshelf is skipped with a warning.

## Troubleshooting

- **A scheduled sync didn't run?** Check `~/.local/share/abp/abp.log`, and run `abp sync <id>` by hand to see its output. `abp cron show` lists what's installed.
- **"playlist on the server does not match after update"?** After every change abp re-reads the playlist to check it. When that check fails abp writes `~/.local/share/abp/mismatch-<id>.txt` comparing what it expected with what the server returned. This message comes from abp, so it won't appear in Audiobookshelf's own logs. Please attach that file if you open an issue.
- **Changed your server or key?** Press `o` in the TUI.

## Releasing

Maintainers publish a release by pushing a version tag; GitHub Actions then tests, builds and publishes it. `make` does the tagging safely:

    make release-patch            # v0.1.7 -> v0.1.8
    make release-minor            # v0.1.7 -> v0.2.0
    make release-major            # v0.1.7 -> v1.0.0
    make release TAG=v0.2.0-rc1   # an exact version; a "-suffix" publishes a pre-release

Add `DRY_RUN=1` to run all the checks and see what would be released without tagging anything. Before tagging it checks that the version is new and not older than the latest release, that you are on the default branch with a clean tree that matches the remote, and that `fmt-check`, `vet` and `test-race` pass. It then asks for confirmation (`YES=1` skips the prompt, `SKIP_CHECKS=1` skips the checks), creates an annotated tag and pushes it. The logic lives in `scripts/release.sh`.
